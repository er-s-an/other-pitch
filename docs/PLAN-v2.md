## 先读这一页

**建议保留 Other Pitch 的名字和“未发生的另一种选择”这一核心，重做产品的参与方式。**

新的产品定义：

> **Other Pitch 把足球回放变成一次你能亲自作出的决定：选择一条路线，看见自己的分支，与原选择比较，再改变一个条件，理解为什么选择的价值会变化。**

英文主张：

> **Your call. Another possibility.**  
> Choose an action. Compare the alternative. Change one condition.

现有项目最需要修复的是“用户作了选择，系统却继续播放同一段内容”。主体验应从单局猜测实际动作，升级为一个约 90–150 秒的三局战术挑战。这个时长是设计目标，须通过试玩调整。

### 本文已经替项目作出的决定

| 决策 | 推荐执行 |
|---|---|
| 主要用户 | 想参与讨论、愿意多懂一点球的普通球迷；先服务这个人 |
| 主要入口 | 半场、暂停、赛后分享或第二屏；先做可独立消费的短回放挑战 |
| 核心问题 | “如果是你，你会怎么处理？” |
| 最重要的交互 | 用户选择真正决定先播放哪条分支；改一项条件后重新比较 |
| 内容规模 | 3 个结构不同的精修场景；另备 1 个未写专属解说的新输入作验证 |
| 首版动作范围 | 地面传球与射门；不做任意自然语言指挥整场比赛 |
| 计分 | 三局选择回顾、发现的战术要点；数值竞技排名延后 |
| 概率展示 | 分清传球完成估计、机会价值、模拟结果频率与 Jev 判断概率 |
| Jev 的角色 | 评估已经算出的分支、挑解释重点、作有边界的语义检查 |
| 微软技术主线 | Microsoft Agent Framework 的真实协作与工具调用；可用时接入实际 Foundry 模型 |
| 页面技术 | 复用现有 Vite、TypeScript、Canvas 与 Python 分析代码，避免同时更换整个技术栈 |
| 最强演示镜头 | 同一局面，只改一个防守条件，路线、比较和解释同步改变 |
| 参赛策略 | 冲综合第一名；分类优先 Best Multi-Agent，按真实完成度决定是否勾选 |
| 工期原则 | 约 44 小时的建议投入；有明确删减顺序，最终至少留一天给验证、录像与提交 |
| 推广与提交 | 本文提供完整材料；实际开户、充值、发布视频、提交比赛不属于本次已执行事项 |

**赢面的来源应是：一段能让人参与的体验，一次能复算的变化，一条确实工作的 Agent 链路，以及一份评委能直接打开的完整作品。**

44 小时估算依赖严格范围：一套短程分支规则、三个精修模板、一个双状态条件、单 Canvas 切换比较，以及真实生产工作流生成后的静态发布包。公开任意输入后端、双屏同步播放器和完整制作后台不计入该估算。

### 1.3 第一名策略怎么落到产品上

五项各 20%，意味着任何一项明显薄弱都会拖累整体。建议每项各准备一项可以直接展示的证据：

| 评审维度 | 最有用的证据 | 当前应该投入什么 |
|---|---|---|
| 技术 | 新的合法合成输入经过同一套引擎得到可复现结果 | 数据契约、真实分支、版本与种子 |
| Agent 创新 | Agent 根据证据选择进一步查询、改写或拒绝输出 | 真实工具调用与有原因的分支处理 |
| 现实影响 | 普通球迷完成体验并能讲出一个取舍；制作人可导出节目包 | 小轮真实试玩、一个最小导出流程 |

## 2. 现有产品为什么不好玩：代码与页面证据

### 2.1 本轮检查范围

读取上述固定提交的 PRD、比赛说明、前端核心、生成器、分析、Agent、QA、MCP 及 trace；并实际打开 [现有网站](https://other-pitch.vercel.app/)完成“播放 → 选择 → 揭晓 → Analyst → Agent trace”。

检查页面时，线上版本显示的是单局 Calder／Okonkwo／Quinn 场景。未对移动端、屏幕阅读器或完整构建链路作全面认证。

| 走查步骤 | 实际状态 | 对产品的影响 |
|---|---|---|
| 1. 打开页面 | 球场与 Play 按钮可见，右侧仍有与局势无关的城市／球场照片 | 视觉注意力没有完全集中在正在作出的决定 |
| 2. 播放与冻结 | 能到达 Guess the pass，出现三项动作 | 已有可复用的回放基础 |
| 3. 选择 Quinn 直塞 | 得到“实际是另一种动作”的反馈 | 用户主动判断的价值没有被承接 |
| 4. 切 Analyst | 显示 EV、xG 和完成率；实际选择与用户选择的文案存在混淆 | 不懂术语的人仍然难以知道自己学到了什么 |
| 5. 打开 trace | 能展示构建时的多阶段记录和拒绝重试 | 是可检查的运行产物，但页面未形成实时请求与本次选择的联系 |

### 2.2 八个要优先处理的问题

**问题一：用户的选择没有改变回放。**  
main.ts 的 choose() 保存 choiceId，之后进入共用 reveal；loop() 继续使用同一组 timeline.frames，paint() 画同一组 ghost。选择主要改变按钮与判词。证据：[main.ts](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/web/src/main.ts)。

**修复要求：**选择 A，先播 A 的球、接球人和关键防守者运动；选择 B，就播 B。不能只把同一条动画换颜色。

**问题二：游戏让用户猜实际动作，产品希望用户理解决策，两者没有连起来。**  
quiz.correct_id 被设置为实际 taken action。当前最佳模型选项与所谓正确选项可以不同。证据：[timeline.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/timeline.py)。

**修复要求：**主问题改为 What would you do?，结果区分 Your choice、Recorded action、Model comparison。虚构比赛中的 recorded action 也必须说明是合成记录。

**问题三：只有一个战术结构。**  
生成器固定 67 分钟、1–1、h8 持球、h3 为实际接球者，并用有限运动锚点生成短片段。seed 主要改变抖动和填充事件。证据：[generator.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/generator.py)。

**修复要求：**增加有不同矛盾的场景，不用“更多随机数”假装内容丰富。

**问题四：不同含义的数字共用了 probability 名称。**  
分析代码的传球 EV 是完成率乘接球点射门 xG；timeline 却把 decision_score 写入 ghost.probability。证据：[analytics.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/analytics.py)、[analyst.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/analyst.py)。

seed 7 的最小逻辑复现结果：

| 动作 | 传球完成估计 | 接球点射门估计 | 当前 EV／直接射门 xG |
|---|---:|---:|---:|
| 实际传 h3 | 0.5409 | 0.0065 | 0.0035 |
| 传 h9 | 0.8746 | 0.7163 | 0.6265 |
| 直接射门 | 不适用 | 不适用 | 0.0581 |

因此 0.63 既不是 0.87 的传球完成率，也不是经真实比赛验证的“63% 进球概率”。这些是当前手写公式的输出。

**问题五：画出了另一条线，没有形成另一个局势。**  
ghost 是贝塞尔展示路径，球员仍沿原轨迹移动；其 source 还被标作 synthetic_tracking。证据：[timeline.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/timeline.py)、[pitch.ts](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/web/src/pitch.ts)。

**修复要求：**分开“合成记录”和“模拟分支”；分支至少让球、持球者、接球者及最近防守者按新动作演进。

**问题六：QA 声明比实际校验能力强。**  
qa.py 主要提取带小数点的数字，与引用中所有数字作匹配。它无法完整验证整数、百分数以及主体、指标、单位是否对应。逻辑复现显示，在引用包含 distance=10.0、EV=0.63、xG=0.06 时，“99% completion”和把 xG 写成 0.63 的句子都可能通过。证据：[qa.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/qa.py)。

**修复要求：**先生成结构化 claim，再由渲染器从 claim 插入数字。不能仅靠自由文本数字扫描。

**问题七：拒绝重试被预先安排。**  
Director 首轮注入 decoy；workflow 甚至在没有 qa_reject 时抛错。证据：[agents.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/agents.py)、[workflow.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/workflow.py)。

**修复要求：**正常运行允许一次通过；另设 Run validation test，明确显示故障注入。演示自然失败时要有当次真实日志。

**问题八：Agent 与界面的关系太远。**  
线上读静态包，trace 的 llm_requested 为 deterministic、llm_notes 为 skipped；现有 LLM 路径仅可选改写几段文案。运动数据也在多个语言包中重复。证据：[trace.json](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/web/public/data/trace.json)、[llm.py](https://github.com/er-s-an/other-pitch/blob/e1b1602a25275e8311711144df476609a665401a/otherpitch/llm.py)。

**修复要求：**保留预生成包的加载优势，同时做一个能展示真实生成、校验与导出的制作入口；同一次运行的输入、结果和 trace 必须能对上。

### 2.3 应该保留什么

已有的合成坐标、Canvas、时间轴、Python 分析函数、Agent Framework 工作流和 MCP 读取工具，都有复用价值。夜场配色与大号标题也可以保留。主要工作应集中在数据语义、状态机、分支和反馈，避免先重写框架或重新做一套营销首页。

## 3. 产品定位、使用场景与成功标准

### 3.1 用户真正要做的事情

普通球迷看到一个处理球瞬间，会产生三个连续问题：

1. 我会怎么踢？
2. 我的选择会付出什么代价？
3. 我漏看了谁、哪条线、哪个时机？

Other Pitch 应让用户通过操作回答这些问题。专业分析工具和播音制作，是这个核心能力的后续出口。

### 3.2 用户与最小价值

| 用户 | 最小可交付价值 | 首版对应功能 |
|---|---|---|
| 偶尔看球的人 | 看懂一个原本没有注意的机会或风险 | 简洁模式、关键人物高亮、短解释 |
| 喜欢讨论战术的球迷 | 比较自己的选择与另一种合理选择 | A/B 回放、统一指标、条件变化 |
| 内容制作人 | 从合成事件获得可审核、可播放的小段节目 | 制作入口、证据、overlay JSON |
| 评委／开发者 | 检查系统是否真的运行、能否复现 | 固定场景版本、真实 trace、MCP 示例 |

### 3.3 具体使用位置

主体验适合半场、暂停或赛后短链接。第一版不宣称已经接入英超直播。制作侧可证明：同一分析包既能成为球迷互动，也能输出一段 12–20 秒的无交互回放图层，未来可嵌入转播工作流。

这些是待验证的产品场景，尚无用户数据证明使用频率或付费意愿。

### 3.4 成功标准

首轮测试使用以下设计目标，不以页面停留时间单独代替价值：

- 新用户无需口头指导，30 秒内作出第一项选择。
- 看过解释后，能指出一个影响选择的具体球员、线路或时机。
- 至少愿意尝试第二局或修改一次条件。
- 能区分“我选了什么”和“合成记录发生了什么”。
- 不会把模型估计理解成官方英超统计。
- 评委可在两分钟内理解产品，并在实际链接里完成同一核心流程。

## 4. 三轮方案推演及最终取舍

### 4.1 三个候选方向

| 方向 | 好处 | 主要问题 | 决定 |
|---|---|---|---|
| A：把现有回放做得更漂亮 | 工期最短，视觉改善明显 | 用户仍是旁观者，单局结束后缺少继续的理由 | 仅保留其中的视觉优化 |
| B：三局“比球员更会踢”的闯关游戏 | 易理解，有成绩和挑战动机 | 容易把简化模型当唯一裁判；与原作的差别还不够深 | 保留短局制，放弃夸张的能力排名 |
| C：选择、比较、改条件的战术沙盘 | 参与、解释和反事实形成同一个闭环 | 需要真实分支与稳定的参数变化 | **推荐主线** |

迭代逻辑：先补“选择有后果”，再补“结果讲得清”，最后补“条件改变后可以再判断”。积分、分享、场景数量服务于这三个环节。

### 4.2 从 AWS × NBA 学什么

据现场观察者 Benx_AI 的[报道](https://benx.ai/blog/posts/nba-hackathon-parallel-world/)，“平行世界”在 Broadcast Code 12 获总冠军及开发者投票最佳视觉奖，展示两个未选传球，并区分数字来源。这是现场报道；未找到主办方独立公开的完整赛果表。少数派同文与个人站是同一作者，不能算两份独立佐证。

可借鉴：固定消费时隙、少字、一次只解释两条替代路线、数值来源清楚。Other Pitch 的新增设计应让观众亲自决定，并通过单一条件变化检验自己的理解。

[“架构 91、视频 38”的复盘](https://builder.aws.com/content/3Kcg7IbLpk8RZ1GA6hGwRcqzZqq/91-38-nba)是战术犯规队员的个人反馈与反思，不能当作本次比赛的权重。可迁移的建议是尽早做成一段外人能看完的完整作品。

另外，[AWS 官方 Leverage Score 案例](https://aws.amazon.com/blogs/media/how-the-nba-and-aws-built-an-ai-system-to-measure-what-actually-wins-basketball-games/)采用数据驱动的预测与反事实归因分层，提示我们把计算、解释和呈现分开；它不能为本项目的合成概率提供准确性背书。

### 4.3 本项目应让评委记住的差异

**观众提出了一个可检验的问题，系统用同一套状态、指标和证据展示条件改变后的差别。**

原创性主要落在可操作的假设、决策回顾与证据交互。避免复刻另一作品的人形发光、碎片转场、光球数量及文案节奏，再仅替换运动项目。

## 5. 完整用户流程与三个场景

### 5.1 一局的完整流程

| 阶段 | 屏幕内容 | 用户动作 | 系统行为 |
|---|---|---|---|
| 进入 | 比分、时刻、进攻方向、“如果是你？” | 点击开始 | 加载该局所需数据；不提前给推荐 |
| 铺垫 | 3–4 秒短进攻 | 看球或直接跳到决定 | 显示球权和关键跑位 |
| 决定 | 2–3 个动作、明确目标 | 点球场目标或同名按钮 | 锁定首次选择，保持匿名局内记录 |
| 自己的分支 | 所选路线先播放 | 看结果或暂停 | 更新球与相关球员；只突出一个关键因素 |
| 比较 | 你的选择、另一选择、合成记录 | 点击 A/B／原记录 | 单 Canvas 切换，从同一决策时刻开始 |
| 改条件 | 一项可改变的假设 | 切换条件并再选 | 重新获取该配置的结果；标明新计算或缓存 |
| 理解 | 一句反馈及可展开证据 | 读一句话、查看原因 | 所有数值与高亮对应本次状态 |
| 下一局 | 下一种战术冲突 | 继续或离开 | 保存回顾；不给强制登录 |
| 三局结束 | 三次选择、要点、挑战链接 | 重试一局或邀请朋友 | 同题再体验，朋友先作答再看比较 |

**决定阶段不要设置强制倒计时。**先让用户看懂，再用可选的 5 秒挑战模式作后续玩法。不可让“反应快”混成“判断好”。

### 5.2 场景一：你漏看了中路

- 叙事情境：沿用虚构球队，67:00、1–1；持球者面前有边路接应和中路跑动。
- 选择：边路传球、中路直塞、直接射门。
- 设计目标：提前看见中路跑动，抓住尚未关闭的机会窗口；条件变化后再认识封线的影响。
- 初始配置：中路有一次可理解的机会；通过真实参数确认，不硬写赢家。
- 可改条件：**最近防守者提前封线**。P0 用预设的两个合法位置，其他输入固定。
- 改后展示：防守者位置、线路封堵、所选分支和机会价值同时更新。
- 反馈例句：“他提前占住了传球线，接球人仍然空着，但球更难送过去。”
- 关键验收：用户选哪条路线就先看哪条；条件变化的解释能指向那名防守者。

### 5.3 场景二：看起来空，不代表接得到

- 叙事情境：边路进攻，远端接球队员有空间，但传球路径经过防守者控制区域。
- 选择：直接横传、短传接应、在可用位置射门；动作配置须符合该局坐标。
- 设计目标：识别传球线路与防守反应。
- 必须避免：所有局都让“直塞”成为最优，或让用户靠按钮位置记答案。
- 第一版只需完成基础场景，不要求再实现一个新条件编辑器。
- P1 变体：接球人启动晚 0.5 秒，数值为场景设计参数；必须驱动运动计算。
- 反馈例句：“空位在接球者身边，危险在球过去的路上。”

### 5.4 场景三：好选择也会失败

- 叙事情境：两项选择的模型价值接近，一项更直接、一项更稳。
- 设计目标：理解风险与收益，以及单次结果不能独自证明决策好坏。
- 主屏可显示“两条路线接近”，不强行只选一个正确答案。
- “更稳”必须引用已计算的完成估计或球权风险；若只实现机会价值，就只解释两条路线的机会质量接近。
- 可以展示一条未成功的合成实际动作，但不据此给用户判错。
- 结果回顾解释用户偏向推进还是保球；三局样本只能说明本次选择倾向。
- 若改变比分或剩余时间，仅改变明确的战术目标或解释重点；除非已实现状态相关策略，不让底层物理概率无故变化。

### 5.5 保留一组新输入，验证系统能处理模板变化

从已有模板保留一组符合相同 schema 的新合法参数；它用于验证，不要求额外制作完整的第四局：

- 不写专属前端条件，不手填它的解释。
- 使用同一导入、分析、分支、Agent、QA、渲染流程。
- 可在开发者视图生成，不一定出现在三局主体验。
- 记录成功、拒绝或缺数据结果；失败时不补造坐标。

这项验证比增加十张题目封面更能证明技术的可延展性。

## 6. 计分、反馈、复玩和分享

### 6.1 第一版不用“猜实际动作”计战术分

三项信息各有用途：

| 信息 | 含义 | 是否判用户对错 |
|---|---|---|
| Your choice | 用户希望执行的动作 | 不直接判 |
| Recorded action | 合成数据里记录的动作 | 不作为正确答案 |
| Model comparison | 在公开假设下，各动作有什么取舍 | 用于反馈，不宣称专业能力认证 |

默认回顾给出“发现中路机会”“看见封堵”“理解取舍”等具体要点。若需要是否达成的判定，必须有公开的场景规则和相近选项处理，不靠 LLM 临场随意夸奖。

### 6.2 数字分数作为可选功能

若试玩证明确实需要成绩，采用“本局相对选择分”，并明确它依赖本局模型：

\[
s(a)=100\cdot \frac{V(a)}{\max_b V(b)}
\]

仅当本局目标明确、所有候选用同一 V 定义、最大值大于小阈值时可用。这个分数不是百分比成功率，也不能跨版本或不同目标比较。模型认为选项接近时给同一档反馈；最大值接近零时不出相对分，改为“此处没有明显机会”。

**本次建议先不把这个分数放主屏。**保留选择回顾，比解释一个人为满分更省成本。

### 6.3 复玩的四个理由

1. 不同局面考察不同因素，下一局有新的矛盾。
2. 改一个条件，会影响刚才的判断。
3. 用户可看自己没选的另一条分支。
4. 同一个局面交给朋友，可以比较各自看到了什么。

不需要积分商城、连续签到、赛季通行证或实时排行榜。

### 6.4 分享的最小实现

P0 做链接复制：

- 分享字段仅含场景 ID、版本、固定 variant，以及可选的发起者动作 ID。
- 接收者首屏隐藏发起者选择及模型排名；作答后才比较。
- 不需要手机号、昵称或账户。
- 链接中的发起者选择可由用户修改，不能作为防作弊成绩证明。
- 场景版本过期时显示明确提示并引导当前可玩版本。
- 分享预览不要泄漏谜底。
- 没有线上统计时，不显示“78% 球迷选了你这条路线”。

图片卡片可在 P1 增加，不能把做海报排在核心交互前面。

## 8. 数据、分支模拟和概率系统

### 8.1 第一条原则：先定义正在估计什么

现有数值混乱不是换一个模型就会自动解决的问题。下一版必须先固定指标名称、时间范围、条件和单位。

以下是**建议实现的数据定义**，不是已经验证的足球预测模型：

| 指标 | 明确定义 | 在产品中的文字 |
|---|---|---|
| p_complete | 在指定动作、起始状态与模拟策略下，最初选定的那次传球由目标队友完成控制的内部估计；非传球动作为空 | Estimated pass completion |
| p_lose_possession | 在共同评估窗口结束或首次射门之前，本方失去控制球权的内部估计；本方丢球即终止该分支评价 | Estimated possession risk |
| q_shot | 对一个合法射门位置及其防守状态计算的 0–1 合成射门质量分，未经过真实比赛校准 | Simulated shot quality |
| V | 同一次本方球权、同一 8 秒窗口内首次合法射门的预期合成质量；未形成射门的路径贡献 0 | Modelled opportunity quality |
| selected_branch_sample | 从某条分支展示的一次代表性或抽样运动过程 | One simulated possibility |
| Jev option probability | Jev 在给定语义问题及选项上的判断分布 | 只在技术视图显示；不作为足球事件概率 |

共同目标暂定为“这个动作在短时间内能创造多好的射门机会”。所有候选动作按相同定义比较：

\[
V(a)=\mathbb E[q_{\text{shot}}\cdot \mathbb I(\text{首次合法射门出现在 }0\!-\!8\text{ 秒内})\mid S_0,a,\pi,\theta]
\]

其中：

- \(S_0\)：选择瞬间的同一状态。
- \(a\)：用户选择的合法动作。
- \(\pi\)：固定并公开的后续行为规则，例如接球后如何控球、何时尝试射门。
- \(\theta\)：模拟参数版本，包括防守反应、球速、启发式质量函数。
- 8 秒是本产品的设计窗口，不是行业通用标准；若修改，需要增加模型版本并重新生成全部可比较结果。

丢球后对手的射门、随后重新夺回球权后的机会，都不属于本次 V。传球飞行、接球、控球和准备射门共同消耗这 8 秒，不能在接球后重新计时。q 使用实际模拟到射门时的位置与压力；统一后续策略指相同的行为规则，不是强行让各分支沿同一轨迹运动。

这不是已经校准的进球概率。内部 V 为 0–1，界面显示“8 秒机会质量：32 / 100”，不能把 V=0.32 写成“32% 会进球”。指标单位标为 normalized_score，不能误标为 probability。如果不能清楚解释 q 的依据，先标为“合成机会评分”并开放公式。

直接射门也进入同一个定义：该次射门就是窗口内的首次射门。传球需要考虑能否完成、完成后能否形成射门、射门时的质量。**不采用“8 秒内射门概率”作为唯一优劣分，因为只要按下直接射门，它就会机械地占优。**

这个短期目标会低估一些长期组织进攻的价值。因此首版只选接近进攻决策的场景，不用同一个分数评价中场控节奏、拖时间或整场胜负。

### 8.2 P0 用解析结果树，P1 再考虑大量随机模拟

在这次时间约束下，推荐先做透明、可复算的有限结果树：

- 射门：按共同时间推进到出脚时，以该时刻的位置和防守状态计算合成质量。
- 传球：传球被截断／完成；完成后，在相同控球策略下形成射门／未形成射门。
- 必要时为“完成后不同接球状态”分配多个离散结果，但不扩成整场比赛树。
- 每个结果有互斥事件、权重和终止状态；同一动作内部的结果权重和为 1。
- 不同动作的 p_complete、V 不要求加总为 1，因为它们是不同条件下的估计。

最简单的传球版本为：

\[
V(\text{pass})=p_{\text{complete}}\cdot p_{\text{shot}\mid\text{complete}}\cdot q_{\text{shot}\mid\text{complete,shot}}
\]

这只有在结果树恰好采用这三个事件定义时才成立；后续分支更多时必须逐叶求和，不能继续套简式。不要把持球未射门的路径错误地算成失去球权；也不要把所有射门终止都算成丢球。

P0 可复用当前 analytics.py 的几何、封线、压力和 logistic 函数作为透明的启发式初始化，将 expected_goals 的对外含义更正为合成射门质量，并保留参数版本。这些系数来自现有程序，不是从真实赛事拟合得到的证据。接球后的统一策略若只判断“能否在窗口内形成合法射门”，p_shot_given_complete 先取 0 或 1；不要凭空再手填一个看似精密的概率。射门质量 q 也不能再次充当“进球概率”抽签。

每个终局至少保存 end_reason（shot／turnover／out_of_play／timeout）、probability、elapsed_s、shot_quality（仅射门有值）、initial_pass_completed、possession_lost、evidence_ids 和 trajectory_id。出界不自动等于丢球，要看重新开球的归属。所有指标从这棵树派生，不分别手填。

**P0 的动画是该模型的一条代表性路径，不是概率计算本身。**例如展示接球成功的路径，同时标明内部估计完成率；不能因为动画里完成了就显示 100%。如果播放一次失败样本，也不能因此把用户判成坏选择。

只有实际实施了抽样模拟，才可写“模拟 N 次”。随机种子固定使实验可复现；复用同一组随机扰动比较两项条件，有助于减少差异中的抽样噪声，但不会自动提高对真实足球的准确性。抽样误差区间与参数不确定性必须分开标注。

### 8.3 先有可解释的运动，再有好看的轨迹

建议首版使用固定时间步长的 2D 运动：

1. 从冻结的起始快照复制出每个动作的独立状态。
2. 为持球者、接球者及关键防守者分别计算运动。
3. 球沿地面路线前进；球速和球员速度受配置上限约束。
4. 防守者按公开策略封堵传球线或靠近目标区域。
5. 判断控制、截断、出界、合法射门、窗口到期。
6. 导出带实际时间戳的帧和事件，前端按时间插值。

其他球员可沿简单区域策略运动，但不能完全沿用“原选择已经发生之后”的轨迹，再宣称他们已经对新选择作出反应。P0 只支持地面传球和射门，不作身体碰撞、空中争顶及完整裁判引擎的承诺。

合法性至少包括：持球队员存在、坐标位于球场、传球目标同队、起点附近有球、时间不倒退，以及所支持动作的基本越位检查或明确的场景约束。为降低工作量，P0 可以仅发布经检查的未越位进攻场景，同时将“尚未实现完整越位判罚”写入开发说明。

球进入球门的动画会给观众很强的确定性暗示。默认在射门发生时结束分支，显示机会质量与下一步的不确定性；若确实展示结果样本，必须标明它只是一个模拟结果。

### 8.4 反事实比较的四个不变量

| 不变量 | 实现要求 | 失败表现 |
|---|---|---|
| 同一决策时刻 | 两条分支共享 base_state_hash 与 t0 | 一条路线在防守已经移动后才开始 |
| 只改变声明的条件 | 记录 intervention 的字段、前值与后值 | 改防守者位置时暗中也调整射门质量参数 |
| 不偷看未来 | 决策只读取 t0 及允许的历史；合成记录的未来只供对照 | 用原比赛后续跑位帮助替代路线 |
| 相同评估规则 | 同一个窗口、后续策略和模型版本 | 给某条路线更长时间或更聪明的接球者 |

“最近防守者提前封线”应落实为一项可审阅的位置变更，并让模拟从该新起点重新计算。若产品以后支持反应延迟，不能把它同时藏在位置变更里。

结果未变时就说“这个条件下结论相近”；不能为了录像好看而让界面强制翻转赢家。展示估计变化、路径变化或取舍变化已经足以表达价值。

### 8.5 来源与不确定性展示

每条证据都要属于明确的一类：

- **Synthetic observation**：生成器写入的合成记录，如起始坐标、比分和记录动作。
- **Derived metric**：由记录与公式计算，如距离、角度、内部完成估计。
- **Simulated branch**：本项目在假设下产生的替代运动、结果树与机会价值。
- **Model interpretation**：模型基于已给证据形成的解释，不是新增观测。

在球场附近常驻简短的 Synthetic scenario 标识；在替代路线标签写 Simulated alternative。解释面板中才展开更细的来源、版本和定义。不要把所有合成坐标称为“真实追踪”，也不要把解释模型称为物理引擎。

## 9. Jev 的具体用法、费用与接入判断

### 9.1 你说的模型确实存在，但免费额度需要改预期

本次核实到的 Jev 是 **TypeSafe AI 的 System One 模型**，提供 Choice、Score、Noul 等结构化判断能力。它的定位适合窄范围的选择、分类和评价，不能直接替代足球状态模拟。[官方发布](https://typesafe.ai/blog/introducing-system-one-models-and-jev) · [模型文档](https://docs.typesafe.ai/models)

官方公开价格为 **每百万输入 tokens 0.042 美元，输出免费**。但官方已经宣布新注册用户暂不再获赠免费额度。因此：

- 不以“注册一定送 5 美元”安排演示。
- 先查看自己的实际控制台余额、可接受的付款方式与额度。
- 若你决定小额充值，几美元足以覆盖大量这种短文本判断；总项目费用还需另算其他模型和托管。
- 本文不包含开户或充值操作。[官方额度更新](https://x.com/typesafeai/status/2104337824292220981) · [控制台](https://console.typesafe.ai/)

证据边界：额度暂停信息来自 TypeSafe 官方账号的公开搜索结果；该帖子全文页面在本次环境受访问限制。没有查到恢复赠送的官方公告，最终以账户页面当时显示为准。

### 9.2 最适合的用法：给出计算结果，让 Jev 挑解释重点

推荐数据顺序：

> 代码生成合法分支和数值 → Jev 判断哪个战术因素最值得解释 → Microsoft 工作流生成并验证面向球迷的内容。

适合交给 Jev 的问题：

| 任务 | 提供的证据 | 可接受输出 |
|---|---|---|
| 选择解释重点 | 各分支的完成估计、机会价值、封线路段、干预差异 | lane_blocked／receiver_space／shot_quality／close_tradeoff |
| 确定叙事角度 | 用户选择、模型差异及目标受众 | missed_option／risk_reward／two_close_options |
| 检查一句话是否与证据相容 | 明确的事实陈述与对应证据 | supported／unsupported／insufficient |
| 选择要高亮的证据 | 已验证的有限 evidence_id 列表 | 从允许的 ID 中选择 |

不交给 Jev 的任务：

- 计算距离、角度、概率乘法和数值排序。
- 推断尚未给出的未来球员轨迹。
- 直接把一个选择概率当成真实进球率。
- 修改底层指标、球员坐标或来源标记。
- 自由决定一个新指标是什么意思。

有一篇直接研究 Jev 的近期预印本，将“代码模拟、Jev 评价”作为核心分工，并报告了依赖未明示环境后果时的局限。其任务包括游戏与其他控制环境，不构成本项目足球准确性的验证；它支持的是这项架构选择。[论文](https://arxiv.org/abs/2610.01834)

### 9.3 三种方案的最终选择

| 方案 | 组成 | 结论 |
|---|---|---|
| A：必要底座 | 确定性计算 + Microsoft Agent Framework + 一个可用解释模型 | 必须先完成 |
| B：有限加入 Jev | A + 一项结构化战术判断，失败可关闭 | **推荐试做，最多半天** |
| C：Jev 主导足球未来 | 把冻结画面交给模型，直接输出“会不会进” | 不采用，难以复算和验证 |

因此答案是：**可以试 Jev；不应该把整个产品和参赛可用性押在 Jev 上。**它必须让一个具体环节更好，而不是成为页面顶部的新徽标。

### 9.4 模型版本与请求约定

截至本次核实，官方已经发布 Jev 1.14.0，而文档中的稳定别名 jev-latest 仍指向 1.13.0。执行时重新查看模型列表，固定一个实际可用、已通过本项目测试的明确版本；不要让自动更新别名在录像和评审之间改变结果。[版本发布](https://typesafe.ai/blog/jev-1-14) · [模型映射](https://docs.typesafe.ai/models)

服务端向官方 System One 接口请求。SDK 与具体字段按接入当天官方 Quickstart、Choice 文档实现；下面是**本项目内部包装契约，不是可以原样发送的供应商请求体**：

~~~json
{
  "task": "select_explanation_focus",
  "task_version": "focus-v1",
  "model_id": "<pin-a-tested-official-model-id>",
  "scenario_id": "central-lane-01",
  "evidence_hash": "sha256:<computed-from-canonical-evidence>",
  "allowed_labels": [
    "lane_blocked",
    "receiver_space",
    "shot_quality",
    "close_tradeoff",
    "insufficient_evidence"
  ],
  "evidence": {
    "selected_action_id": "pass_central",
    "metric_ids": ["m_complete_central", "m_value_central"],
    "intervention_id": "defender_closes_lane"
  }
}
~~~

实际请求必须包含各 evidence_id 对应的事实值与定义，不能只提供上面用于简化展示的 ID。英文结构化事实先接通；中文在前端或解释环节呈现，不默认不同语言的判断表现相同。

返回值只允许写入 interpretation 层，保存所选标签、选项分布、模型 ID、耗时及输入证据哈希。Choice 的分布在给定选项间归一化；其 confidence 反映判断集中程度，不能当成经验准确率。[Choice](https://docs.typesafe.ai/primitives/choice) · [Confidence](https://docs.typesafe.ai/confidence)

若分布很平、关键证据缺失或标签非法，回退为规则选出的解释重点。规则回退应在内部 trace 标明，用户仍可正常回放。

### 9.5 5 美元到底够不够：按输入量算

下表是使用官方单价的**算术估算**，不是实际账单。假设没有额外费用；不包含 Foundry、其他模型、托管、税费或视频工具。

| 用量假设 | 输入 tokens | 估计 Jev 费用 |
|---|---:|---:|
| 1 次短判断，每次 2,000 tokens | 2,000 | $0.000084 |
| 100 次同规模判断 | 200,000 | $0.0084 |
| 1,000 次同规模判断 | 2,000,000 | $0.084 |
| 1 次完整体验：3 次调用，每次 2,500 tokens | 7,500 | $0.000315 |
| 1,000 次上述完整体验 | 7,500,000 | $0.315 |
| $5 全用于输入 | 约 1.19 亿 | 约 59,523 次 2,000-token 调用 |

建议开发试验预算先设 **$0.10–$0.50 的内部目标**，先确认供应商最低充值额；额度很小也不要每帧调用模型。对相同证据和任务版本缓存结果，记录真实输入量，再决定扩大。

比单价更容易拖慢项目的是：拿不到可用账户、请求契约不熟、输出语义误读，以及为了展示一个模型而增加过多界面。

### 9.6 半天接入实验与退出门槛

建议用 40 个开发样例和 20 个保留样例检查结构化任务。它们是项目自建的小规模测试集，不是足球预测 benchmark。

开发样例覆盖：

- 传球线路被封、射门角度差、两项接近、缺少关键证据。
- 同样内容的选项顺序变化和表述变化。
- 数字看起来很高、但对应了错误动作或错误单位的干扰。
- 一项条件变化后，应该随之改变的解释重点。
- 必须选择 insufficient_evidence 的情形。

标签依据明确场景规则，由作者逐项复核。20 个保留样例在提示词冻结后只作一次正式结果记录；修改提示后，它们就不再是独立留出样例。

按独立局势划分开发与留出；同一局势的改写、翻译、选项重排必须留在同一个集合。主观解释允许多个合理标签，先写可接受集合，不能为了方便统计强迫每题只有一个答案。

**通过门槛是建议值：**所有输出都能解析、没有越权修改事实或引用不存在的证据；关键缺证据样例不被武断通过；保留样例至少 18/20 符合预先写好的可接受标签，且明显优于或更简洁于现有规则基线。小样本结果只证明这批任务是否值得接入，不能宣称“90% 足球准确率”。

如果规则本身已经足够，或 Jev 只会复述最大的 V，就关闭这项实验。把时间还给分支体验与录像。

## 10. Agent、MCP、证据校验与失败处理

### 10.1 从“六个阶段都有名字”转为三项真实判断

保留现有 Microsoft Agent Framework 基础，但让需要语义判断的角色有明确输入、允许的工具和交付物。计算、格式转换、验证、渲染都是有用的工程节点，无需把每个函数包装成一个自主 Agent。

| 角色 | 真正负责的判断 | 工具／输入 | 必须交付 |
|---|---|---|---|
| Moment Director | 候选瞬间是否有值得比较的选择；证据不足时补查还是跳过 | 候选事件、快照读取、可用字段 | DecisionBrief：时刻、候选动作、选择理由及所需证据 |
| Replay Analyst | 应检查哪些分支与战术因素；不替代计算器做数学 | 合法动作、分支模拟、指标读取；可选 Jev 评价 | AnalysisBundle：指标引用、对比维度及不确定性 |
| Fan Editor | 怎样把取舍讲清；简洁／分析视图分别需要什么 | 已验证分析、受众配置、有限解释模版 | ExplanationSpec：主句、证据引用、高亮和展开项 |

同一托管模型可以为多个角色服务；不必购买三个不同模型。关键在角色边界、证据传递和可观测行为。让 Analyst 选择工具查询和解释角度，同时让确定性函数计算 V，是合理分工。

官方 Agent Framework 支持 Agent 与显式工作流组合。比赛作品可以将运行时协议、工具与框架贡献讲清楚，无需声称每一步都由 LLM 完成。[Microsoft 文档](https://learn.microsoft.com/en-us/agent-framework/overview/)

### 10.2 推荐工作流

~~~mermaid
flowchart TD
  I["合成输入"] --> V["结构与合法性检查"]
  V --> D["Moment Director"]
  D --> M["通过 MCP 读取证据"]
  M --> A["Replay Analyst"]
  A --> S["代码计算动作分支"]
  S --> J{"启用 Jev 评价？"}
  J -->|是| E["结构化解释重点"]
  J -->|否| F["Fan Editor"]
  E --> F
  F --> Q{"逐条证据校验"}
  Q -->|通过| B["发布回放包"]
  Q -->|可修复且未超次数| F
  Q -->|不可修复| X["拒绝该片段或安全模版"]
~~~

图中框架编排、MCP 工具、数学计算、Jev 与解释模型是不同组件。评审说明按实际调用如实列出，不把 Jev 写成微软模型。

### 10.3 MCP 要有真实调用，不止一个可启动的服务

建议复用现有 Python MCP 服务，先做一个真实客户端贯通。最小工具面如下，名字是建议：

| 工具 | 输入 | 返回 |
|---|---|---|
| get_decision_snapshot | scenario_id、t0 | 快照、来源、完整性状态 |
| list_legal_actions | snapshot_id | 已验证动作与不可用原因 |
| simulate_branch | snapshot_id、action_id、允许的 intervention_id、model_version | 分支引用、结果树、指标 ID |
| get_evidence | evidence_ids | 带单位、主体和时间范围的事实 |
| get_published_bundle | scene_id、version、variant | 已校验产物及生成信息 |

如果为了节省实现只保留前四个，也足以展示有意义的工具消费。运行记录要能证明：

1. 一个实际客户端连接成功。
2. Agent 发起了某次读取或模拟调用。
3. 工具结果中的 ID 进入了最终解释。
4. 缺字段或错误 ID 导致具体失败处理。

本地 stdio MCP 可以是真实 MCP 使用；不等于 Azure MCP Server。A2A 可以在比赛后用于跨组织的独立服务，此刻不是必要门槛。

### 10.4 QA 升级：校验“谁的什么数值”，而不是到处找数字

每条数值陈述先生成结构化 Claim，再由代码渲染成文本：

~~~json
{
  "claim_id": "claim-001",
  "subject": {
    "scenario_id": "central-lane-01",
    "action_id": "pass_central",
    "variant_id": "base"
  },
  "metric_id": "m_complete_central",
  "metric_name": "p_complete",
  "raw_value": 0.72,
  "unit": "fraction",
  "display_value": "72%",
  "evidence_id": "ev-central-base-001",
  "definition_version": "football-toy-v2",
  "time_window_s": 8
}
~~~

上面 0.72 只是契约示例，不是对现有场景的预测。验证需要同时满足：

- evidence_id 确实存在于本次结果包。
- subject 与 action、variant、时间范围匹配。
- metric_name、单位及显示转换正确，例如 0.72 → 72%。
- 数值来自同一个指标，不能拿距离 10.0 解释成 xG 10.0。
- 允许合理四舍五入，但禁止跨指标寻找一个“差不多”的值。
- 机会价值不能带“进球概率”标签；小数、整数和百分号都要覆盖。
- 个性化完成后再次校验，不让翻译或改写引入新数字。

语义陈述如“防守者封住了线路”，采用受约束的类型与对应证据字段，例如 lane_interception_risk 增加、拦截区域与路径有交集。LLM 可写连接语，但不能自由增添未经结构化支持的球员身份、历史战绩或结果。

Jev 可以辅助筛查语义，但不是绕过结构验证的许可。

### 10.5 失败应该成为可信行为

| 情况 | 产品行为 | trace |
|---|---|---|
| 输入缺少关键坐标 | 不生成具体替代轨迹；给出可读的缺失原因 | rejected_input + missing_fields |
| 一句解释引用错误 | 有限次修复；成功后继续 | claim_rejected → revised → validated |
| 普通输入首次通过 | 直接发布 | validated_first_pass |
| 解释模型超时 | 使用从相同证据渲染的简洁模版 | fallback_template |
| Jev 不可用 | 跳过可选评价，继续规则重点与主解释 | optional_evaluator_unavailable |
| 模拟本身失败 | 不显示旧场景冒充本次结果；保留上一有效界面并提示 | simulation_failed |
| 用户打开验证测试 | 显式注入一个预设错误，展示拒绝原因 | fault_injection=true |

正常运行绝不强制“先错一次”。演示可主动点击 Run validation test 展示故障注入，但字幕和页面都应说明这是测试。一个清晰的真实拒绝，比固定表演“六个 Agent 正在思考”更有说服力。

### 10.6 什么时候生成，必须说清楚

本方案允许两条诚实的路径：

- **发布前生成：**真实工作流先产出校验包，公众即时读取。页面标记生成时间、版本与 Cached validated result。
- **按需生成：**若后端已经稳定托管，用户触发任务后实际执行工作流，显示真实 run_id 与状态。

缓存结果不是假 AI。把缓存执行记录描述为用户刚触发的新计算，才会损害可信度。视频中的日志必须对应所展示的场景、配置和包版本；若展示的是发布前运行，就明确标为 producer generation。

## 11. 数据契约、接口和仓库改造图

### 11.1 建议的核心对象

| 对象 | 必须字段 | 作用 |
|---|---|---|
| DecisionSnapshot | schema_version、scenario_id、t0、pitch、players、ball、context、provenance、state_hash | 固定选择瞬间，隔离未来信息 |

| BranchResult | action_id、variant_id、model_version、policy_version、horizon_s、outcome_tree、frames_ref、metrics | 存放计算和运动 |
| MetricEvidence | evidence_id、metric_name、value、unit、subject、definition、source_ids | 防止跨指标挪用数值 |
| ExplanationSpec | audience、headline、claim_ids、highlight_ids、limits、fallback_status | 驱动两种模式 |
| ReplayBundle | bundle_id、scene_id、variant、branches、recorded_action、explanations、validation、generation | 前端唯一消费的主产物 |
| RunTrace | run_id、framework、actual_model_ids、steps、tool_calls、timings、errors、cache_status | 核验真实执行 |
| ChallengeSession | scene_versions、choices、variant_ids、completed_rounds | 本地保存进度与链接分享 |

证据 ID 可以是可读短 ID；涉及复现与缓存的哈希要由规范化对象真正计算，不能手填一个看起来像哈希的字符串。

### 11.3 页面与接口的最小方案

**P0 静态发布包：**

- GET /data/v2/scenes.json：场景目录、版本和可玩 variant。
- GET /data/v2/{scene}/{variant}/bundle.json：所需回放包。
- motion 文件按所选分支加载；共享起始片段只加载一次。
- trace、详细证据与额外语言在用户展开时加载。
- 分享 URL 使用固定的 scene／version／variant／可选 choice 参数，前端校验允许值。

**可选托管生成服务：**

- POST /api/runs：只接受登记过的场景和允许的干预，不接收任意模型提示词。
- GET /api/runs/{run_id}：返回 queued／running／passed／failed 与产物引用。
- GET /api/runs/{run_id}/trace：经过密钥和敏感字段清理的运行记录。
- 简单轮询就够；无需为了展示进度引入复杂消息队列或流式服务。

同配置命中缓存时返回 cache_hit 与原始生成时间；新生成成功前不能把旧值标成新值。静态版本切换到另一预计算 variant 也需要明确这一点。

## 12. 前端体验、视觉与交互规范

### 12.1 首屏只承担一个任务：让人愿意作出选择

保留 Other Pitch 的名称与夜间球场质感，但把无关城市／球场照片从主体验移走。

推荐首屏内容：

- 顶部：Other Pitch；右侧 How it works 与可展开的 About this model。
- 球场上方：What would you do?
- 一句任务：Create a better chance in the next 8 seconds.
- 中央：能看清球、持球者、两名候选接球者与关键防守者的球场。
- 下方：一个 Start the play 按钮；已熟悉用户可以直接跳到决定时刻。
- 角落：Synthetic scenario · About 2 minutes。

这些都是目标文案，不能在尚未形成三局流程时把时长写成已测量数据。

第一轮无需解释所有技术。用户开始后再依次看到选择、分支、取舍与证据。

### 12.2 视觉系统的具体取舍

| 项目 | 推荐 |
|---|---|
| 场地 | 复用 2D Canvas；略深的草地，边界线有足够对比 |
| 球员 | 两队明确区分；持球者、目标球员和关键防守者增加号码／外圈，不只靠颜色 |
| 足球 | 与球员区分的高对比实体，运动时可保留短尾迹 |
| 你的路线 | 实线与明确文字 Your choice |
| 对照路线 | 切换到单独状态；需要预览时用虚线，并标明 Recorded 或 Simulated |
| 信息层级 | 先结果解释，再指标，再技术详情；不同时铺满四个面板 |
| 字体 | 优先复用现有可用字体；正文清楚，标题不必极度夸张 |
| 动效 | 服务球与人的运动；减少与战术无关的滚动动画 |
| 声音 | 默认关闭；有余力时加入轻提示音，不能影响理解 |

不必重做品牌全套。最值得花时间的是：三秒内找到球、看懂谁能接球、知道下一步点哪里。

### 12.3 P0 的 A/B：一个 Canvas，一键切换

44 小时计划不包含双屏同时播放或拖动擦除比较。

采用单球场：

- Your choice / Recorded action / Another option 三类清楚标注。
- 选择切换时回到共同的 t0，保持相同播放速度。
- 显示相对于决策时刻的秒数；比赛时钟另列，避免 67:00 和分支 +2s 混淆。
- Compare 按钮能暂停并切换；“回到选择”保留场景与条件。
- 不一次叠加全部球员位置与所有轨迹，避免球场成为难读的线团。

条件变化属于另一个明确维度：Base / Defender closes the lane。不要让“比较动作”和“改变条件”共用一个含糊的开关。

### 12.4 简洁模式与分析模式真正不同

| 视图 | Casual | Analyst |
|---|---|---|
| 主要文字 | 一句具体解释 | 主张、指标、假设和来源 |
| 数值 | 最多两项；先说明含义 | 完成估计、机会价值、球权风险及结果树 |
| 图层 | 球路与一名关键防守者 | 拦截区域、相关位置、指标高亮 |
| 不确定性 | “One simulated possibility” | 指标定义、模型版本、窗口、敏感性 |
| 技术 trace | 收起 | 可展开，但不抢占主回放 |
| 切换 | 保留当前进度与选择 | 保留当前进度与选择 |

建议把 V 内部保留为 0–1 归一化值，界面显示为 **Opportunity quality: 36 / 100**，同时写明是合成模型分数。传球完成率仍可显示为 **Estimated completion: 72%**。两者使用不同格式，降低误读概率。

如果第二项指标解释成本太高，Casual 只显示一句具体因果与一个有名字的分数；并不要求为了“专业”填满所有数字。

### 12.5 必须覆盖的交互状态

| 状态 | 处理 |
|---|---|
| 首次加载 | 简洁占位与可读说明；不要假装 Agent 正在运行 |
| 包加载失败 | Retry；可以返回场景列表；不白屏 |
| 用户快速切换两条分支 | 取消或忽略过期请求，旧帧不能覆盖新选择 |
| 条件包尚未加载 | 保持上一有效画面，新状态确认后再更新标题与指标 |
| 分享链接参数无效 | 提示该挑战不可用，提供当前题目 |
| 场景版本更新 | 给出版本提示，旧选择不自动当作新成绩 |
| 返回上一局 | 保留所选动作和已探索分支 |
| 关闭标签页后回来 | 可恢复本地进度，也提供 Restart |
| 减少动态效果 | 允许逐步或静态对照，保留相同信息 |
| 手机横竖切换 | 重新布局，不重置游戏 |

移动端至少人工检查 390px 左右宽度与常见桌面宽度。推荐按钮可点击区域不小于 44px，使用原生可聚焦按钮、清楚的焦点样式和可读的状态文本；这些是本项目设计要求，不是本轮已经取得的无障碍认证。

## 13. 部署、费用、可用性和降级

### 13.1 默认架构：公开体验稳，真实生成有证据

建议把比赛版本固定为：

> 现有 Python 生产流程 → 实际 Agent／MCP 运行 → 校验并导出不可变回放包 → 现有 Vite／Vercel 站点公开播放。

这让公开核心体验不依赖观众提供 API Key，也不需要每次点击消耗模型额度。场景一的两个条件配置，都通过同一套真实计算流程产生；切换时如实显示为预计算结果。

制作侧先提供 CLI 或极简本地界面：选场景 → 生成 → 看验证报告 → 导出 JSON。评委在网站检查已发布结果和经过清理的 trace，在仓库复现生成。若提交说明承诺在线重新生成，才必须把这项服务实际托管并保证评审可用。

公开任意输入生成、完整制作后台、远程多租户 MCP 和数据库，都不计入 44 小时。

### 13.2 第一个执行小时解决模型可用性

仓库计划的 GitHub Models 已不可用。官方文档明确其 playground、catalog、inference 与相关功能已于 2026-07-30 退役；不能把仓库中的旧地址当作免费备用通道。[官方退役说明](https://docs.github.com/en/github-models)

推荐顺序：

1. 确认现在手头已经可用的模型账户与额度。
2. 若符合条件，检查 Azure for Students；官方提供免信用卡的学生入口及 $100／12 个月额度，但是否通过资格、能否使用某个模型与区域配额，需要账户内确认。[官方学生计划](https://azure.microsoft.com/en-us/free/students/)
3. 对一个可用 provider 完成最小真实模型调用，并接到现有 Agent Framework。
4. 保存模型 ID、区域／入口类型、请求成功与否及额度状态；不保存密钥。
5. 如果 60–90 分钟内无法取得 Foundry 可用通道，停止反复换区试错，先用框架支持且自己已可用的 provider 完成生产流程。

使用 Microsoft Agent Framework 本身可以如实写进项目。只有实际调用了 Foundry 才声称使用 Foundry；若分类要求该能力而未完成，就不勾选相应分类。不要把申请资格、领取到通用信用额度和成功部署模型当成同一件事。

本次规划不要求绑卡或自动切换付费订阅，也不把学生资格或免费容量写成保证。

### 13.3 什么时候值得增加在线后端

只有以下条件同时成立才做：

- 一局完整的选择、比较和改条件已经稳定。
- 三局和分享的完整目标已经完成，或已正式决定缩减。
- 用户测试证明“自己给新状态”比其他改进更有价值。
- 账户、托管方式和评审期间可用性已经确认。
- 至少留出一天独立处理网络失败、超时和错误日志。

后端可继续使用现有 Python，选择当前确实可用的一处托管环境；有已验证 Azure 资源时可考虑合适的 Azure 服务。不要把迁移 Vercel、换前端、改运行时和接入新模型同时打包成 P0。

### 13.4 费用控制与评委可用性

| 费用项 | 处理 |
|---|---|
| Jev | 小规模试验、按证据哈希缓存、记录实际输入；开关独立 |
| 解释模型 | 生成时按有限场景调用；按真实供应商报价估计，本文不虚构统一单价 |
| 托管 | 保留当前可用站点；执行者核对账户限额，不默认任何套餐永久免费 |
| 图片／视频生成 | 主片使用实际录屏；无需额外购买生成式视频额度 |
| 日志 | 保留足够复核的结构化记录；不上传无意义的大量帧与密钥 |
| 公共试玩 | 发布包静态读取，核心体验不因模型预算耗尽而关闭 |

“内部预算上限”用于控制生产过程，并不是向评委设置付费墙或要求其自带密钥。若某项公开实时功能无法持续提供，就在提交前缩减对该功能的承诺，并保留免费完整可玩的核心体验。

建议把首次生产预算设为自己可接受的小额目标，再依据真实调用量调整。Jev 的 $5 不能证明整个系统总成本只有 $5。

### 13.5 最小运行卫生

API Key 只在服务端或本地环境变量中使用，不放进前端 bundle。公开 trace 清理认证头、密钥、私人路径与账户信息。缓存键绑定输入、参数和版本，避免错拿另一个条件的结果。

用户只需要完成挑战时，不收集邮箱、手机号或真实身份。测试数据记录匿名编号与具体行为即可，不为了几次试玩增加用户系统。

## 14. 验收、用户测试与结果记录

### 14.1 核心验收矩阵

以下是要执行的验收，不是已经全部通过的结果。

| 编号 | 检查 | 通过条件 |
|---|---|---|
| A01 | 选择确实改变回放 | 两个合法动作具有不同 branch_id，球与相关球员的后续状态不同 |
| A02 | 起点公平 | 所有候选共享快照、时刻与评估窗口；无原记录未来数据泄漏 |
| A03 | 时间定义 | 传球飞行、控球和准备射门均计入共同 8 秒，接球后不重新计时 |
| A04 | 指标可复算 | 从互斥终局计算的 V、完成估计和丢球风险与输出一致 |
| A05 | 概率与范围 | 每个动作的终局权重和为 1；合法范围、空值语义正确 |
| A06 | 条件变化 | diff 只有声明字段；重新计算所得证据、分支和解释对应新配置 |
| A07 | 变化不被表演化 | 没有显著差异时允许显示接近，不强制翻转最佳选项 |
| A08 | Claim 绑定 | 错动作、错指标、错单位、整数百分比、不存在的证据 ID 被拒绝 |
| A09 | 正常与故障测试 | 正常首轮通过有效；故障注入有标识，不能自动混入普通运行 |
| A10 | 真实 Microsoft 框架运行 | 能找到实际 provider／model、角色交接、工具结果和最终产物 |
| A11 | MCP 客户端 | 真实调用返回值进入可核验的 evidence／claim；缺数据分支行为正确 |
| A12 | 保留输入 | 未写专属解说的一组新合法参数能走完流程，或有明确拒绝原因 |
| A13 | 页面状态 | 快速切换、返回、加载失败不串场，不用旧数据冒充新条件 |
| A14 | 模式与语言 | Casual／Analyst 的指标一致；最终显示内容经过验证 |
| A15 | 分享 | 新窗口先作答再看朋友选择；坏参数、旧版本有可用处理 |
| A16 | 停用可选模型 | Jev 停用或超时后，公开核心三局仍可完成 |
| A17 | 初次访问 | 无登录、无自带 key 要求，普通浏览器能完成主流程 |
| A18 | 交付版本 | 网站、视频、公开仓库、生成参数与说明对应同一候选发布版本 |

对计算模块写有意义的单元测试，重点覆盖这些错误；不为每一段文案和每个按钮样式编写重复实现的测试。

可以额外选 20–30 组合法参数检查速度、边界、概率守恒与缓存一致性，但它们只验证模拟器内部性质，不验证真实比赛预测准确率。不要用大量同模板 seed 作为“训练数据规模”宣传。

### 14.2 试玩：6–8 人够发现主要体验问题

推荐实际邀请 6–8 人，其中有经常看球者，也有偶尔看球者。该数字是计划，不是已经取得的样本。

每次约 10 分钟，先不解释产品答案。中性任务：

1. “请打开这个链接，按你的理解玩。”
2. 完成第一局后问：“刚才你做了什么选择？页面告诉了你什么？”
3. “请改变页面允许你改变的一项条件。”
4. “你觉得这个数字代表什么？”
5. “你愿意再玩一局或发给朋友吗？如果不愿意，是什么原因？”

不要问“你是不是觉得改条件很酷”，也不要一边指导一边把顺利完成算成自然完成。

### 14.3 记录表与建议门槛

| 观察项 | 记录方式 | 用途／建议目标 |
|---|---|---|
| 到第一次选择的时间 | 从可交互首屏到点击选项 | 目标 30 秒内；过长就简化入口 |
| 是否看懂自己选了什么 | 原话复述 | 至少 5/6 人不把它理解成纯播放按钮 |
| 是否明白改了哪个条件 | 原话指出人／位置／结果 | 至少 5/6 人能指出这一项变化 |
| 是否误读机会价值 | 记录其对分数的解释 | 任何“它保证会进球”都值得修文案 |
| 是否自愿开始第二局 | 行为计数 | 用于判断复玩，不只问喜欢不喜欢 |
| 是否愿意分享 | 是否实际复制／发起分享动作 | 不把口头称赞当作分享率 |
| 哪处卡住 | 时间点、界面状态、原话 | 优先修最常见阻碍 |

5/6 等门槛只是小轮发布判断。对外报告写“6 位试玩者中 5 位能独立说出改变的条件”，不要扩大成“83% 用户提升战术能力”。

若要与现版比较，用少数人交替体验顺序、换等难度题目，记录完成与理解差异；这个小实验仅提供方向，不作统计显著性或因果提升承诺。

### 14.4 比赛材料只使用实际结果

允许写入 Pitch 的内容：

- 实际场景数、真实完成的变体数。
- 实际调用过的微软组件与 MCP 工具。
- 实际观察到的用户反应与人数。
- 实际测量的加载、生成与播放时间，附测量条件。
- 被验证系统拒绝的具体错误实例。

不能先在文案里写“理解提升 40%”“80% 准确率”“毫秒级全部生成”，再去找数据填空。

推荐把一页 validation-report.md 和一页 user-test-notes.md 放进最终仓库，由执行者在测试发生后填写日期、版本、过程和结果。

## 16. 114 秒视频分镜、英文口播和制作方法

### 16.1 视频只回答一个问题

> “用户亲自改变一个条件后，这个产品能不能让他看懂选择为什么变化？”

目标成片 114 秒，给“少于 2 分钟”留下编码与片尾余量。以下分镜是**完成 P0 后的录制脚本**；当功能缩水时必须同步改口播，不得先拍出不存在的能力。

主片使用实际工作网站录屏，技术片段使用真正生成对应回放包的工作流记录。英文口播与英文字幕是推荐交付。不要用长片头、模型 logo 墙或纯幻灯片取代功能演示。

### 16.2 完整时间轴

| 时间 | 画面与操作 | 英文口播 | 这段要证明什么 |
|---|---|---|---|
| 0–12s | 直接出现冻结球场与三个选择；短标题 Your call. Another possibility. | Every football fan has asked, “Why didn’t they try that pass?” Other Pitch turns that question into a decision you can explore. | 痛点与产品主张 |

| 34–56s | 切换 Defender closes the lane；同一球场显示唯一位置变化；重新播放并对齐比较，留约 2 秒观察 | Now I switch to a second defensive setup, where this defender closes the passing lane. | 91–107s | 切到实际已完成三局的回顾；字幕 Completed session recap；复制挑战链接，在新窗口先作答 | After three rounds, this recap shows my decisions and what I explored. A friend can open the same challenge and choose before seeing my answer. | 完整性、复玩与分享 |
| 107–114s | 网站 URL、项目名与最后一帧球场；不再新增信息 | Other Pitch. See the options. Understand your choice. | 清楚结束与可访问入口 |

这套口播约 200 词，最终以实际朗读和剪辑为准。若英文速度较慢，优先删技术句子的修饰语；不要把全片加速到难以理解。

### 16.3 录像真实性与连贯性

- 条件变化使用预计算配置时，界面保留 Cached validated variant；不是实时生成就不放“Live AI rerun”字幕。
- 技术记录是生产时运行，就使用过去时 produced，画面明确 Producer generation。
- 三局回顾来自真实完成过的会话；不暗示前面一分钟已经连续玩完全部三局。
- 不通过剪掉重大失败伪造成功率，也不通过剪辑暗示未经测量的即时模型响应。
- 若最终只有两局，把 three rounds 与相关屏幕全部改成 two rounds；一局版改为 “Review the choices you explored”。
- 如果未接 Jev，视频完全可以不提 Jev；如果接入，把它放技术说明里的实际评价步骤，不抢走产品高潮。
- 改条件后只需证明路径和取舍发生可解释变化；不要声称“推荐必定逆转”。

### 16.4 录制和剪辑步骤

1. **10-24 粗录：**用真实网站先把故事走通，发现需要多少点击与等待。
2. 冻结一个候选版本和场景配置，记录 commit、bundle 与 run_id。
3. 清空无关标签页、私人通知、账户页与调试密钥。
4. 推荐以 1920×1080、16:9 录制；这是制作建议，不是额外赛事规格。
5. 鼠标移动慢一点，点击前后保留足够停顿；重要变化尽量发生在同一区域。
6. 分段录旁白，用自己的声音即可；没有必要购买配音或模仿名人。
7. 裁掉无关等待，保留操作因果；字幕每次只表达当前这一点。
8. 原创轻音乐可选，最省事的是不配音乐。不要默认球赛转播音轨可以使用。
9. 导出后完整看一遍有声版，再看一遍静音字幕版。
10. 用实际文件检查时长、分辨率、字幕是否遮住按钮；确认公开链接在未登录窗口可播。

执行者可以用 ffprobe 检查最终时长，命令示例：

~~~bash
ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 other-pitch-demo.mp4
~~~

这次文档没有生成视频文件；脚本、分镜、操作顺序与验收已经完整给出。

### 16.5 缩到 90 秒时，怎么删

先删三局回顾中的停顿、技术节点的细节和重复定义，保留“选 → 看分支 → 改一个条件 → 看解释变化”。不要把最有辨识度的干预压成一闪而过的动画。

### 17.4 回答十个难问题

**Q1：为什么要用 AI？不就是几条分支加按钮吗？**

分支与按钮本身用普通代码就能实现。AI 的价值在于把新的合成状态组织成可讲的片段、选择解释重点，并针对不同观众产出基于同一证据的说明。我们通过一组未写专属解说的新输入，验证工作流能处理模板变化；不把固定计算器伪装成 AI 创新。

**Q2：为什么需要多个 Agent？一个提示词也能写解释。**

简单场景一个提示词可以完成部分工作。这里把选片、分析查询、观众解释分开，使各自允许读写的内容可控，失败可以定位到某一步。数值仍由代码计算。用真实证据传递与修订记录说明这种分工的收益，不宣称单 Agent 绝对做不到。

**Q3：这些概率准确吗？**

当前使用合成状态与透明的内部模型，尚未用真实比赛校准。完成估计、机会质量和模型解释分布分别标注。我们验证的是内部一致性、条件变化与解释是否忠于计算；真实世界准确性需要有使用权的数据和独立验证。

**Q4：既然是假数据，这有什么现实价值？**

比赛版本证明交互与生产流程可以让人看懂取舍，并测试不同受众需要多少解释。它不能证明已经可以指导职业球队。下一步用获得授权的历史数据检查相同流程，并让内容制作人与球迷验证实际使用场景。

**Q5：这是不是 AWS × NBA“平行世界”的足球版？**

借鉴的是体育反事实表达的清晰度。Other Pitch 的重点是让观众主动选择、改变一个假设、比较自己和朋友的判断，并追溯解释依据。我们承认灵感来源，也通过实际交互机制说明自己的贡献，不推测其他作品一定没有某项功能。

**Q6：为什么还需要 Jev？微软模型不能做吗？**

Jev 是可选的窄任务评价器，用来从已有证据中挑战术解释重点。主流程、数值和公开回放不依赖它。如果小测试没有显示价值，我们就不使用它。微软框架承担实际的编排与角色协作；服务归属如实列出。

**Q7：条件改动只是切换两段预制动画吗？**

公开版本复用已计算并校验的两个配置，避免每次点击都等待模型。两者由同一引擎从只差一个字段的状态产生，运动、结果树和解释均绑定配置与版本。我们可以展示参数差异、生成命令以及保留输入验证，证明它不是独立编写的两段结论。

**Q8：模型为什么有时拒绝输出？是不是系统坏了？**

关键位置缺失或解释与证据不符时，输出具体轨迹会误导用户。系统会指出缺什么、有限次修复或使用有依据的简洁模版。普通有效运行可以一次通过；人为故障注入会单独标记。

**Q9：谁会使用或付费？**

当前先验证普通球迷是否愿意继续玩和分享。潜在商业客户是体育内容制作方、俱乐部媒体与持有数据权利的转播方，可能购买可嵌入的互动内容或制作工具。付费意愿仍是待验证假设，不能凭潜在市场大小替代实际访谈。

**Q10：接真实比赛后，最难的是什么？**

不仅是换数据源。需要时间同步、球员身份映射、追踪缺失处理、动作合法性、模型校准与使用权；真实球员会对替代行动作出未观测的反应。产品必须继续显示假设与不确定性，不能把合成版本的参数直接称为真实预测能力。

### 17.5 三个最值得主动展示的证据

1. **同一配置的可复算变化：**展示唯一干预字段、真实生成结果与对应画面。
2. **一组未预先适配的输入：**同一代码与解释流程成功处理，或诚实拒绝缺失数据。
3. **一次具体错误被拦住：**例如把另一动作的完成估计贴过来，Claim 验证明确指出主体不匹配。

这三项比额外堆模型名称更能帮助评委判断技术是否扎实。

## 18. 比赛后路线与商业验证

### 18.1 第一阶段：验证人们愿不愿意继续玩

比赛后两周内，继续测试：

- 三局中哪一局最容易促使用户主动重试。
- 改条件后，用户是否能讲出变化原因。
- 挑战链接是否真的被朋友打开与完成。
- 一周后是否仍愿意玩新的局面。

只有这些行为出现，才值得增加题库、每日挑战或个人历史。不要先做积分经济、社交关系链和付费墙。

### 18.2 第二阶段：验证制作侧是否节省工作

找实际制作体育内容的人，用同一包尝试：

- 选择需要解释的时刻。
- 审阅来源和模型假设。
- 导出图层、短解说、字幕或结构化节目包。
- 修改一条解释后重新校验。
- 记录从输入到可用片段的真实耗时，与其现有流程比较。

可以先从学校球队、业余俱乐部或拥有素材权利的小型创作者开始合作。合作、访谈、数据获取都需要另行实际发生；这份文档不会把它们写成已建立的伙伴关系。

### 18.3 第三阶段：数据与模型升级

拿到合法数据后，分别推进：

1. 输入质量与追踪对齐。
2. 传球、控球、射门等事件模型的校准与独立验证。
3. 对未选动作的合理反应假设，评估哪些条件最影响结论。
4. 不确定性和失效场景的可视化。
5. 专业人士审阅解释，而不是只审阅模型分数。

真实已发生事件可以用于验证部分预测；没有发生的反事实不能直接获得完整真值。要区分“预测已发生事件的表现”与“替代路径是否合理”，不能用前者证明后者全部正确。

### 18.4 商业路径的优先级

| 路径 | 先验证的问题 | 当前优先级 |
|---|---|---|
| 面向球迷的免费挑战 | 是否会继续玩、是否真的分享 | 高，验证体验核心 |
| 内容方的互动组件 | 是否能放入其文章、直播间或短视频链路 | 中，先做试用 |
| 制作人的回放工具 | 是否省时且有足够可审阅性 | 中，找真实工作流程 |
| 面向职业教练的决策产品 | 是否有可信数据、校准与战术适用性 | 低，先不作专业承诺 |
| 直接卖个人订阅 | 是否有稳定内容供给与复访 | 延后，不由一次比赛热度推出 |

不需要为了 Pitch 虚构一个精确 TAM 或引用没有来历的“体育 AI 百亿美元市场”。一项明确的使用习惯和一位真实制作人的反馈更有用。

### 19.3 什么时候可以停止开发

达到以下条件就停止加功能，转向交付：

- 外部用户可以独立完成一局选择、比较和条件变化。
- 本局结果与证据可复算，未发现跨动作／跨版本串用。
- 至少两个有不同职责的实际模型阶段通过共享证据协作，MCP 调用可核查。
- 公共体验稳定，视频能在规定时间内讲清楚。
- 未实现的能力已从主界面和提交文案中删去。

完整三局是优先目标；一个可信完整的版本比多个半成品更适合提交。对第一名的追求不应让最终交付晚于截止时间。
